## D15. サイト固有の設定をどこに置くか

関連する要件: §0-4、1-6
状態: **決定済み（2026-11-02）**

**決定**: `metadata` コレクション（1 エントリ、`routable: false`）に置き、標準のエントリ編集画面で編集する。EmDash 自身が読む値（`title` / `tagline` / `logo` / `favicon`）は Settings に残す。

**理由**: サイト設定のスキーマは拡張できない（F-01）。`social` は 6 サービスの固定列挙で、要件の booth に枠がない。置き場所の候補は 3 つあったが、

- プラグインの設定ストアは `site/` から読む REST 経路が文書化されていない（F-11 周辺）
- 自前の管理ページは、画像フィールド 2 つのためにメディア選択 UI を自作することになる。文書化された入手元がない（F-12）
- コレクションは文書化された読み取り API に最初から乗り、`cms-client` の実装も変わらない

境界は「**誰が読むか**」で引いた。EmDash が読む値は Settings、`site/` だけが読む値は `metadata`。`admin.astro` が Settings の Site Icon を管理画面の favicon にフォールバックさせるため、この境界には実体がある。

**留意**: 1 エントリであることは強制されない。`hidden: true` にすると導線は消えるが URL 直打ちで 2 件目を作れる（F-11 周辺）。運営のみが触るため、強制は入れなかった。サイドバーに 1 件だけの一覧が出る点は受容する。

## D16. 画像を WebP に揃える方法

関連する要件: 5-3、4-2、4-3
状態: **決定済み（2026-11-02）**

**決定**: 変換はブラウザで行う。管理画面に「Convert images」ページ（`webp-only` プラグイン）を置き、`media:beforeUpload` で WebP 以外のアップロードを全経路で拒否する。サーバーでは変換しない。

**理由**: 制約はディスク容量（個人契約のサーバー）。4K の PNG スクリーンショットは WebP の数倍になる。

- サーバー変換は 4K で**ピーク +236 MiB**（F-23）。項目 4 の合格基準（4-2: ピーク 350MB 未満）を 1 件で超える。同時 2 件で +470 MiB
- 外部サービスへの切り出しは、クライアント側フックが無いため標準 UI を保てず（F-04）、`media:afterUpload` 経由では PNG が一度ディスクに載る。さくらの AppRun は共用型でも月額上限 3,720 円で、得るものがない
- 拒否だけでは編集者が詰まる。編集者は変換手段を持たない

拒否と変換ページは同じプラグインに同居させた。片方では成立しない組み合わせのため。

**留意**: 標準の画像フィールドを保つため、変換は別ページになる。編集者は「変換 → ライブラリから選ぶ」の 2 段になる。エントリ編集画面のパネルに置くことは Block Kit の制約でできない（F-14）。署名付きアップロード（S3 互換）に移すと `media:beforeUpload` の適用時点が文書で確認できていないため、`local` ストレージ前提。

## D17. セットアップ完了までの Discord ログイン封鎖

関連する要件: 2-5、2-9
状態: **決定済み（2026-11-02）**

**決定**: `guard.ts` に、`emdash:setup_complete` が立つまで `/_emdash/api/auth/discord/` を 403 で閉じる判定を追加する。

**理由**: 空の DB で Discord ログインを先に通すと Editor が 1 人作られ、以降 `POST /_emdash/api/setup/admin` が `ADMIN_EXISTS` で拒否されるため、**Admin を永久に作れなくなる**（F-07）。`users:manage` は ADMIN 限定なので昇格させる主体が存在せず、復旧は DB の直接編集のみ。踏みやすさに対して代償が大きい。

**留意**: EmDash 側の挙動（ユーザーが 1 人でもいれば Admin 作成を拒否）は、ユーザーテーブルが空になった半端な状態からの復旧を意図したもの。外部 ID プロバイダがユーザーを自動生成する構成と組み合わさると罠になる。上流の不具合ではなく、組み合わせの問題。

## D18. 宣言で表現できない制約をどう実装するか

関連する要件: 0-3、0-6、5-2
状態: **決定済み（2026-11-02）**

**決定**: 制約は seed の `options` に宣言し、プラグインの `content:beforeSave` が強制する。プラグインは設定を持たない。全キーを列挙したカタログを持ち、カタログに無いキーは拒否する。

**理由**: 画像の寸法（F-02）、リッチテキストの範囲（F-05）はフィールド定義では表現できない。一方 `content:beforeSave` は保存を拒否できる（F-03）。`schema:read` でフィールドの `options` を読めるため、**宣言は seed の 1 箇所で済む**。

全キーの列挙は、許可リストだけでは不足だったため。推測で書いた許可リストは実キーと一致せず（`codeBlock` ではなく `code`、`html` ではなく `htmlBlock`）、コードブロックと生 HTML が素通りしていた（F-20）。カタログがあれば、未知のキーは「許可されていない」ではなく「認識できない」として止まる。

この形を取ったプラグイン:

| プラグイン | 強制するもの |
|---|---|
| `image-dimensions` | 画像フィールドの寸法 |
| `portable-text-policy` | リッチテキストの型・見出し・マーク・リスト |
| `webp-only` | アップロードの形式（seed ではなく一律） |

**留意**: 編集者が気づくのは保存時。ツールバーは配置できないため（F-05）、使えてしまってから止まる。CSS でボタンを隠すことはできるが、TipTap のキーボードショートカットと Markdown 入力規則（` ``` `、`# `）は塞げないので、拒否が本体で非表示は補助になる。

## D19. 使わない EmDash 機能をどう扱うか

関連する要件: 0-3、5-1
状態: **決定済み（2026-11-02）**

**決定**: 使わない 8 機能（コメント / メニュー / リダイレクト / ウィジェット / セクション / タクソノミー / 執筆者 / インポート）は、**書き込みを全員に対して 403 で拒否し、サイドバーの導線を CSS で隠す**。読み取りは拒否しない。EmDash 自身の画面は URL では到達可能なまま。

**理由**: 使わない subsystem が、誰も読まない状態を増やすのを防ぐ。403 にしたのは、ルートが存在し呼び出し元が認証済みである以上、運営に伝えるべきは「機能が無効」であって「存在しない」ではないため。

読み取りを拒否しないのは、管理 UI の画面を消せないため（F-17 / F-12）。画面が開いて保存だけが拒否される形のほうが、404 で壊れて見えるより分かりやすい。

**留意**: 導線の非表示は DOM に依存する。サイドバーは `href`（ルーティング契約の一部）を足場にしており比較的安定だが、エディタのパネルは中身の文字列を足場にしており弱い。効かなくなった場合は項目が戻るだけで、データには影響しない。

「無効化」と「自前画面への差し替え」は別の決定なので、ピックのリストを 2 つに分けている（`DISABLED_FEATURES` / `REHOMED_FEATURES`）。設定 > SNS は後者（D15 でメタデータ側へ移したため隠す）。

## D20. 型チェッカを導入するか

関連する要件: 1-2、5-6
状態: **決定済み（2026-11-02）**

**決定**: `@astrojs/check` 0.9.12 と TypeScript 6.0.3 を devDependency に入れ、`pnpm check` を追加する。

**理由**: EmDash のビルドは型検査をしない。導入した直後に、生成された `emdash-env.d.ts` が構文エラーになっている不具合を検出した（F-18）。`.d.ts` が壊れていると他の型エラーも一切出ないため、検出手段が無い状態が続いていた。

TypeScript は 6 系に固定する。`@astrojs/check` の peer が `^5.0.0 || ^6.0.0` で、7 系は不適合（最初に 7.0.2 が入り peer 警告が出た）。

**留意**: Node 系ツールの追加なので、`avoid-node-python-dependent-tools` の観点では増やしたくない依存。ただし Astro 公式のツールであり、検出した不具合の重さが上回ると判断した。

## D21. 待機時のメモリ増加をどう扱うか

関連する要件: 4-6
状態: **決定済み（2026-11-03）**

**決定**: **毎日 7:00 に CMS を再起動する。** 4-6 の不合格はこれで受け入れる。漏れ自体の調査はしない。

**理由**: 6 時間の実測で、立ち上がり後に 0.13 MiB/時 の一定の増加が続くことが分かった（減速しない。21502 サンプル中 2 回しか下がらない）。合格基準「RSS が単調増加しない」は満たさない。

ただし率が小さい。154.6 MiB から 350 MiB までの余裕 195 MiB を使い切るのに約 62 日かかる。**毎日の再起動なら間隔中の増加は約 3 MiB** で、余裕の 1.5% にすぎない。

再起動が安全であることは確認済み。EmDash 1.3.1 のビルド成果物に `setInterval` が 1 つもなく、予約投稿はクエリ時に可視になる方式なので、**再起動が発火ウィンドウを跨いで予約投稿を落とす危険がない**（F-28）。起動は 1 秒で、公開サイトは静的配信のため閲覧者に影響しない。編集者が作業中の時刻を避けて 7:00 とする。

**留意**: この判断は**待機時の増加にしか効かない**。4-2（編集 30 分）では 185 → 212 MiB と 30 分で 27 MiB 増えており、負荷時の蓄積は 2 桁速い。長時間の編集セッションは測っていないため、編集中に上限へ近づく可能性は残る。1 日分の編集が余裕 195 MiB に収まるかは未確認で、`restart: always` による復帰が最後の砦になる。

増加の原因は特定していない。要求が健康確認の 1 回だけでタイマーも動かない状態で増えており、V8 のヒープ断片化か SQLite のページキャッシュが候補だが裏付けていない。毎日再起動する前提では調べる価値が小さいと判断した。
