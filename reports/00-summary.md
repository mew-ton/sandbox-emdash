# EmDash 採用可否 — 総括

調査の要件（問い・検証内容・合格基準・判定のルール）は [`docs/requirements.md`](../docs/requirements.md)。
このレポートの番号（1-1〜4-7、構成案 A / B）はすべてその文書の番号を指す。

調査対象: emdash 1.3.1（2026-10-18 公開）、Astro 7.4.2、Node 24.22.1。すべてローカル（Node / ローカル Docker）で検証した。

要件番号に紐づかない EmDash 自体の能力・限界は [`findings.md`](findings.md)、調査中に決めたことは [`docs/decisions.md`](../docs/decisions.md)。各要件の検証がどこまで実機で確かめられているかは下の「[検証の鮮度](#検証の鮮度)」、調査を完了させるために残っている作業は [`open-items.md`](open-items.md)。

## 結論

要件 §3 の判定表に照らすと、**残る不合格は 4-6 と 5-6 の 2 件だけ**で、どちらも受け入れ方針を決めてある
（[D21](../docs/decisions.md#d21-待機時のメモリ増加をどう扱うか) / [D22](../docs/decisions.md#d22-メンバーが落とせるクラッシュ5-6をどう扱うか)）。

| 構成案 | 成立条件（要件 §3） | 現状 |
|---|---|---|
| A: headless + `cms-client` 維持 | 項目 1・2・3（3b）・4・5 がすべて合格 | **項目 1・2・3・6 は合格。** 残るのは 4-6 と 5-6 で、いずれも対策付きで受容を決定済み。成立とみなすかは「対策込みの受容を合格と数えるか」の判断（下記） |
| B: 公開サイトと CMS を統合 | 項目 2・4・5 が合格し、配信方式と §0-1 を緩める意思決定がある | 4-6・5-6 は A と同じ。加えて **§0-1 を緩める意思決定が無い**ため、こちらは条件が欠けたまま |
| 見送り（PocketBase 継続） | 2-2 / 2-3 / 2-5 / 2-6 のいずれかが不合格 | 該当しない（いずれも合格） |

**未決の判断が 1 つ残っている。** 4-6 と 5-6 は基準そのものは満たしていない。対策（毎日の再起動、
journal 監視からの通知）を前提に受容したので、これを「項目 4・5 が合格」と数えるかどうかで A の成立が決まる。
数えるなら A は成立し、数えないなら要件 §3 の成立条件を書き換える必要がある。

項目 5（セキュリティ）は調査開始後に追加し、A・B 共通の前提として扱う。

**推奨は構成案 A。** 残る 2 件の中身:

- **4-6: 待機時に RSS が 0.13 MiB/時 で増え続ける。** 6 時間完走、減速なし。350 MiB までの余裕 195 MiB を
  使い切るのに約 62 日。原因は未特定（タイマーも無く、リクエストも無い状態で増える）。
  **毎日 7:00 の再起動で間隔中 +3 MiB** に収まる（D21）。EmDash に `setInterval` が 1 つも無く、
  予約投稿はクエリ時に評価されるため、再起動が何も取りこぼさない（F-28）。
- **5-6: 一般メンバーが 1 リクエストで CMS を落とせる。** 配列フィールドに型違いの要素を約 15 万個入れた
  書き込みで Node が落ちる。zod を上げても直らない。**偶発では踏めず**、内部犯か乗っ取られたセッションで
  のみ到達、影響は可用性のみ。防がずに `restart: always` で復帰させ、**journal 監視から Discord へ通知**する（D22）。
  根本遮断は上流修正待ち（D11）。

どちらも EmDash 側の仕様・実装が原因なので、構成案 B を選んでも解消しない。

**A を選ぶ場合の運用・配置条件**:

| | 内容 |
|---|---|
| 毎日 7:00 の再起動 | D21。4-6 の受容条件 |
| journal を追う監視ユニット | D22。5-6 の受容条件。`Failed with result` と `restart counter is at` を Discord へ |
| Node のポートを直接叩けない配置 | 5-5 の前提。転送ヘッダの無い要求はレート制限が効かない |
| `pnpm-workspace.yaml` を本番イメージへ同梱 | 5-6 の zod override が外れないようにする（`bench/prepare.sh` で確認済み） |

判定自体は変わっていないが、[`findings.md`](findings.md) の F-01〜F-05（拡張性の限界）により、**構成案 A で必要になる自前実装が増えた**。宣言で表現できない制約（画像の寸法、リッチテキストの範囲、アップロード形式）はすべてプラグインになる。合否には影響しないが、保守量の見積もりに影響する。

## 検証の証拠

これは採用可否を判断するためのサンドボックスで、成果物は**各要件を個別に検証して合格した事実と、その証拠**である。常に最新のコードが全項目を通ることは求めていない。`verify/*.mjs` と `bench/` は回帰テストではなく、ある時点で証拠を作る計測器であり、その後コードが進んでも**既に得た証拠は失効しない**。

必要なのは、各 # について「何で、いつ、どのコードに対して確かめたか」が辿れること。下の表はそれを記録する。

合否だけでなく、**何でどこまで確かめたか**を記録する。要件 §2 の合格基準を満たしたと言えるのは「実機」「自動」「計測」のいずれかで確認した場合で、「コードのみ」は読み取りに基づく推定にすぎない。

| 記号 | 意味 |
|---|---|
| 実機 | 動かして確認した（ブラウザ・実 Discord・HTTP） |
| 自動 | `verify/*.mjs` が確認した |
| 計測 | `bench/` で測った |
| コードのみ | ソース・ドキュメントの読み取りのみ。実行していない |
| 未検証 | 確認していない |

### 本日の変更が以前の証拠に対して持つ意味

2026-11-03 に実装を変えた。**以前の証拠が無効になるわけではない**（それぞれ上のコード状態に対する事実として有効）。確認すべきは、変更が合格基準から外れていないか、だけである。

| 要件 | 変えたもの | 基準から外れるか |

| 1-1 / 5-1 | 匿名に閉じるルートと無効機能の拒否を別 middleware に分離し、無効機能の書き込みを 404 → **403** に変えた | **外れない。** 5-1 の基準は「塞いだものは 404/403 を返す」で、どちらも許容されている |
| 1-6 | seed に `metadata`・リレーション・`options` を追加 | 外れない。空の DB からの再現は実機で確認した（下記） |

| 5-7 | 監査ログを `middlewares/audit-log/` に移動 | 外れない。記録内容は変えていない |

したがって**どの要件も、合否を書き換える必要はない**。新しい証拠が欲しい # があるときに、その計測器を回せばよい。手順は README「自動検証」節。

| D14 | 全般 | セキュリティ設定・秘密の持ち方 | **採用: 非秘密の保護設定はビルドに焼き込む**（付け忘れで保護が外れない）。**秘密はビルドにも env にも置かず**、実行時に root 所有ファイル / Docker・systemd secret から読む。デプロイ固有の識別子だけ env |

## 構成案 A で必要になる作業

### スキーマの移行

- `articles` / `casts` を EmDash の seed（`cms/seed/seed.json`）として定義する（このサンドボックスの定義は検証用の最小形）
- PocketBase のフィールドとの対応: リッチテキスト → Portable Text、ファイル → メディアライブラリ + 画像フィールド、select → select、カンマ区切り → string、JSON → json
- スキーマ変更の手順: admin か CLI で変更 → VPS 上で `emdash export-seed` → 差分をコミット

### cms-client

- 本番の PocketBase 版 `cms-client` の `.d.ts` と、このサンドボックスの `cms-client/dist/index.d.ts` を突き合わせる（`ColorThemeBase` / `FetchOptions` / `Cast` は仮定義）
- private registry への公開設定、`CMS_URL` / `CMS_TOKEN` を CI の secret に登録
- 読み取りトークンの発行手順（サービスアカウントを Admin で招待 → トークン発行 → Subscriber へ降格）を運用手順に入れる

### 認証・cold-standby の再設計

- 本番用 Discord アプリ（client secret、redirect URI）、Bot（再確認を使う場合）、ロール ID の登録
- 実 Discord での未確認は 1 点に減った。**PKCE は受け付けると確認済み**（F-25）。残るのは Bot での単一メンバー取得に特権 Intent が要らないことで、これはログイン中セッションの定期再確認（2-6）にのみ必要。ログイン時のロール判定は OAuth の `guilds.members.read` で足りる
- メール送信プラグインの選定（D5）と、cold-standby の切替手順（env を `on` にして再起動、戻すときも再起動）
- セットアップは `EMDASH_SETUP_TOKEN` を設定してから行う。可能なら公開前に VPS 内で済ませる

### 運用手順の改訂

- バックアップ: SQLite のオンラインバックアップ（`sqlite3 .backup` / `node:sqlite` の `backup()`）と `uploads/` を定期取得（D1 で (a) の場合）
- 公開・非公開化・削除で CI を起動するフックの dispatch 先と token を env に設定。dispatch 失敗時の再試行が無いので、定期ビルドを併用する
- 運営の追加は `EMDASH_ALLOW_INVITES=on` で再起動 → 招待 → 受諾 → `off` で再起動
- EmDash の更新時: 注入ルートの差分確認（D6）、`emdash types` / OpenAPI からの型再生成、項目 1〜3 の検証スクリプトの再実行

### セキュリティ（項目 5）

- 保護設定はビルドに焼き込み済み（5-1 の塞ぐルートと `mcp:false`、5-5 の `trustedProxyHeaders`、5-6 のセッション 1h 既定、5-7 の監査ログ）。デプロイ時の env 付け忘れで外れない（D14）
- 秘密（鍵・client secret・トークン）はビルドにも env にも置かず、root 所有ファイル / Docker・systemd secret を起動時に読む（D14）
- Node ポートはプロキシ経由のみ到達可能にする（127.0.0.1 バインド / ファイアウォール）。TLS 終端のプロキシで HSTS を付け、アクセスログを有効化（5-4 / 5-5 / 5-7）
- `pnpm.overrides.zod` を入れるときはクリーンインストールで反映を確認し、`pnpm audit` だけを信じない（5-6 / D10）
- 5-6 のメンバー crash を EmDash 本体へ報告（D11）。当座は `restart: always`、`DISCORD_SESSION_MAX_AGE_SECONDS=3600`（乗っ取り窓の短縮）、監査ログで受容
- 監査ログ（`cms/src/middlewares/audit-log/index.ts`、5-7 / D12）を journald/収集で箱の外へ退避し、リバースプロキシのアクセスログも有効化。バックアップ・エクスポートパッケージ（ユーザーの email を含む）の保管先を決める（5-8）
- 更新のたびに `verify/item5-security.mjs` と `bench/security/dos-poc.mjs` を回し、`pnpm audit` を確認する

### データ移行（範囲外のため変換規約の下書きのみ）

| PocketBase | EmDash | 変換 |
|---|---|---|
| レコード ID | エントリ ID（ULID、新規採番） | 旧 ID → 新 ID の対応表を残す（公開 URL に ID を使っているなら必要） |
| `created` / `updated` / 公開日時フィールド | `createdAt` / `updatedAt` / `publishedAt` | 作成 API の `publishedAt` 指定は Editor 以上で可 |
| HTML 本文 | Portable Text | HTML → Portable Text 変換が要る（EmDash の WordPress 取り込みは Gutenberg 用の変換器を持つが、汎用 HTML 用は未確認） |
| ファイルフィールド | メディア（アップロード API）+ 画像フィールドの `{ id, alt }` | ファイルを API でアップロードし、返った ID を参照に入れる |
| ユーザー | Discord 経由の初回ログインで自動作成 | 事前移行は不要（著者の対応付けは email） |
