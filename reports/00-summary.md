# EmDash 採用可否 — 総括

調査の要件（問い・検証内容・合格基準・判定のルール）は [`docs/requirements.md`](../docs/requirements.md)。
このレポートの番号（1-1〜4-7、構成案 A / B）はすべてその文書の番号を指す。

調査対象: emdash 1.3.1（2026-10-18 公開）、Astro 7.4.2、Node 24.22.1。すべてローカル（Node / ローカル Docker）で検証した。
Discord は実物を使わずモックで検証した（実物で手元確認する手順は [`providers/discord/README.md`](../providers/discord/README.md)）。

## 結論

要件 §3 の判定表に照らすと、**どの構成案も、現時点では成立条件を満たしていない**。

| 構成案 | 成立条件（要件 §3） | 現状 |
|---|---|---|
| A: headless + `cms-client` 維持 | 項目 1・2・3（3b）・4・5 がすべて合格 | 不成立。項目 1 の **1-7 不合格・1-8 一部不合格**、項目 4 の **4-6 未完**、項目 5 の **5-6・5-7 不合格**。項目 2・3（3b）は合格 |
| B: 公開サイトと CMS を統合 | 項目 2・4・5 が合格し、配信方式と §0-1 を緩める意思決定がある | 不成立。4-6 未完、5-6・5-7 不合格、§0-1 を緩める意思決定もまだ無い |
| 見送り（PocketBase 継続） | 2-2 / 2-3 / 2-5 / 2-6 のいずれかが不合格 | 該当しない（いずれも合格） |

項目 5（セキュリティ）は調査開始後に追加し、A・B 共通の前提として扱う。

**推奨は構成案 A。ただし先に片付けるべき所見が増えた。** 以前からの 3 件（1-7・1-8・4-6）に加え、セキュリティで 2 件:

- **5-6（最優先）: 一般メンバーが 1 リクエストで CMS を落とせる。** 配列フィールドの検証を失敗させる書き込みで Node が落ちる（約 2MiB の本文、10MiB 制限の内側）。zod を上げても直らない。上流への報告と緩和が要る（D11）。
- **5-7: 操作の監査ログが core に無い**（公開・削除・権限変更が記録されない。D12）。

1-7 と 5-6・5-7 の原因は EmDash 側の仕様・実装なので、構成案 B を選んでも解消しない。

## 合格しなかった項目

| # | 要件で求めていたこと | 実際に起きたこと | 影響 | 関連する意思決定 |
|---|---|---|---|---|
| 1-7 | `emdash site export` で全データを書き出し、空のインスタンスへ取り込むと、**コンテンツ・メディア・ユーザーが欠けずに戻る** | コンテンツとメディアは戻ったが、**ユーザーが戻らない**。EmDash のサイトエクスポートは、仕様としてユーザー・passkey・トークンを持ち出さない（取り込み時は著者を移行先の既存ユーザーへ email で対応付けるだけ） | 要件の「1-7 不合格なら headless 運用は不可」に該当する。ただし統合構成（B）でも同じ | D1 |
| 1-8 | headless 運用で依存する API が**すべて OpenAPI 文書に載っている** | `cms-client` が使う読み取り API は載っている。**API トークン発行・招待・メディアファイル本体の配信の 3 ルートが載っていない**。設定更新 API は文書（`PUT`）と実装（`POST`）が食い違っている | 載っていないルートは EmDash の更新で予告なく変わりうる。トークン発行と招待は運用（CI 用トークンの作成）に必要 | D2 |
| 4-6 | 24 時間放置して **RSS が単調増加しない** | **計測を 46 分で打ち切った**。その間の変動は 1 MiB 程度だが、24 時間分の判定はできていない | 未判定のため、項目 4 を「全合格」とは言えない | D8 |
| 5-6 | `pnpm audit` で high 以上が無く、更新を追う手順がある | zod 4.5.4（CVE-2023-54404、high）を EmDash が固定。override で audit は clean にできるが、**一般メンバーが約 2MiB の書き込み 1 回で CMS を落とせる**経路が残り、zod を 4.6.7 に上げても直らない（SIGSEGV、再起動まで到達不能） | 認証済みメンバーによる可用性低下。繰り返し送れる | D10, D11 |
| 5-7 | 誰がいつ公開・削除・権限変更したかを追える | core は MCP 呼び出しとエクスポート/インポートしか監査ログに書かない。通常の操作は記録されず、記録には非公式プラグインが要る | インシデント時に操作者を追えない | D12 |

| # | 要件 | 実際 |

| 5-1 | 未認証で届くルートが分類され、不要なものは塞がれている | 既定では公開サイト用・MCP 用 OAuth・画像サービスなど 12 系統が未認証で届いた。middleware（`cms/src/security/public-surface.ts`）と `mcp: false` で塞いで合格にした |

| # | 要件で求めていたこと | 実際 |

## 意思決定が要る事項

| # | 関係する要件 | 事項 | 選択肢 |
|---|---|---|---|
| D1 | 1-7 | 「全データが戻る」をエクスポート機能で満たすことを必須にするか | (a) ユーザーを含む完全復元は SQLite のバックアップ + `uploads/` で行い（この方法ではユーザーまで全部戻ることを確認済み）、`site export` はコンテンツ移送用と位置づける（1-7 の合格基準を緩める）/ (b) 要件どおり必須とし、A も B も不成立とする |
| D2 | 1-8 | OpenAPI に載っていないルートへの依存を許容するか | (a) トークン発行・招待は admin 画面での手作業とし自動化しない。`cms-client` が依存するのは文書化された読み取り API と `url` 値のみ（1-8 の合格基準を緩める）/ (b) 不可とする |
| D3 | 2-4 / §0-3 | 一般メンバーを Editor にすることで生じる、§0-3 に無い権限（タクソノミー・メニュー等の作成更新、他人の記事の公開・非公開化）を許容するか | 許容 / 公開操作もガードで制限する（追加実装） |
| D4 | 2-6 | Discord API に到達できないとき、ログイン中のセッションを上限時刻まで維持するか | 維持（現状）/ 拒否 |
| D5 | 2-7 | cold-standby 用のメール送信手段 | 非公式プラグイン（各 1 名メンテナ）/ 自作 |
| D6 | 2-5 | EmDash 更新時に、新しいログイン経路が増えていないか注入ルートの差分を確認する運用 | 受け入れる / 受け入れない（他経路の封鎖を保証できなくなる） |
| D7 | 1-1 | メディアファイル配信に認証が無く、下書きでしか使っていない画像も URL を知っていれば取得できること | 許容 / 別ストレージ・プロキシで制限 |
| D8 | 4-6 | 24 時間放置の計測が未完であること | 採用判断の前に 24 時間分を取り直す（スクリプトはそのまま再実行できる）/ 46 分の観測で足りるとする |
| D9 | 4-7 | サンドボックス用プラグイン（workerd）を将来使う可能性 | 使うなら待機時で 250 MiB を超えるため、1 GB プランが前提になる |
| D10 | 5-6 | zod の脆弱性（high）への当座の対応 | `pnpm.overrides.zod = 4.6.7` を入れる（audit は clean になる。ただしクリーンインストールでしか効かず、メンバー crash は残る）/ EmDash 本体の更新を待つ |
| D11 | 5-6 | 一般メンバーが 1 リクエストで CMS を落とせる経路（zod 更新でも残る） | (a) EmDash 本体へ報告し、上流修正まで採用を保留 / (b) 当座の緩和（`restart: always`、メンバーのレート制限、リバースプロキシで本文サイズをさらに絞る）を入れたうえで受け入れる。※緩和はいずれも 1 回の停止は防げない |
| D12 | 5-7 | 操作の監査ログ | 非公式の `@emdash-cms/plugin-audit-log`（v0.2.3、メンテナ数要確認）を入れる / 同等のネイティブフックを自作する / 監査ログ無しを受け入れる |
| D13 | 5-5 | 総当たり対策が既定で無効なこと | 本番で `EMDASH_TRUSTED_PROXY_HEADERS`（例: `x-forwarded-for`）を設定して IP 単位で効かせる。設定しないとログイン・magic link のレート制限が素通りする |

## 構成案 A で必要になる作業

### スキーマの移行

- `articles` / `casts` を EmDash の seed（`cms/seed/seed.json`）として定義する（このサンドボックスの定義は検証用の最小形）
- PocketBase のフィールドとの対応: リッチテキスト → Portable Text、ファイル → メディアライブラリ + 画像フィールド、select → select、カンマ区切り → string、JSON → json
- スキーマ変更の手順: admin か CLI で変更 → VPS 上で `emdash export-seed` → 差分をコミット

### cms-client

- 本番の PocketBase 版 `cms-client` の `.d.ts` と、このサンドボックスの `cms-client/dist/index.d.ts` を突き合わせる（`ColorThemeBase` / `FetchOptions` / `Cast` は仮定義）
- private registry への公開設定、`CMS_URL` / `CMS_TOKEN` を CI の secret に登録
- 読み取りトークンの発行手順（サービスアカウントを Admin で招待 → トークン発行 → Subscriber へ降格）を運用手順に入れる

### 認証・cold-standby の再設計

- 本番用 Discord アプリ（client secret、redirect URI）、Bot（再確認を使う場合）、ロール ID の登録
- 実 Discord で未確認の 2 点（PKCE の受け付け、Bot での単一メンバー取得に特権 Intent が要らないこと）を確認
- メール送信プラグインの選定（D5）と、cold-standby の切替手順（env を `on` にして再起動、戻すときも再起動）
- セットアップは `EMDASH_SETUP_TOKEN` を設定してから行う。可能なら公開前に VPS 内で済ませる

### 運用手順の改訂

- バックアップ: SQLite のオンラインバックアップ（`sqlite3 .backup` / `node:sqlite` の `backup()`）と `uploads/` を定期取得（D1 で (a) の場合）
- 公開・非公開化・削除で CI を起動するフックの dispatch 先と token を env に設定。dispatch 失敗時の再試行が無いので、定期ビルドを併用する
- 運営の追加は `EMDASH_ALLOW_INVITES=on` で再起動 → 招待 → 受諾 → `off` で再起動
- EmDash の更新時: 注入ルートの差分確認（D6）、`emdash types` / OpenAPI からの型再生成、項目 1〜3 の検証スクリプトの再実行

### セキュリティ（項目 5）

- 未認証で届く不要ルートを塞ぐ middleware（`cms/src/security/public-surface.ts`）と `mcp: false` を本番にも入れる（5-1）
- `EMDASH_TRUSTED_PROXY_HEADERS` を設定してレート制限を効かせる（5-5 / D13）。TLS 終端のプロキシで HSTS を付ける（5-4）
- `pnpm.overrides.zod` を入れるときはクリーンインストールで反映を確認し、`pnpm audit` だけを信じない（5-6 / D10）
- 5-6 のメンバー crash を EmDash 本体へ報告し、採用可否を判断（D11）。当座は `restart: always` とメンバーのレート制限で影響を小さくする
- 監査ログ（5-7 / D12）とバックアップ・エクスポートパッケージ（ユーザーの email を含む）の保管先を決める（5-8）
- 更新のたびに `verify/item5-security.mjs` と `bench/security/dos-poc.mjs` を回し、`pnpm audit` を確認する

### データ移行（範囲外のため変換規約の下書きのみ）

| PocketBase | EmDash | 変換 |
|---|---|---|
| レコード ID | エントリ ID（ULID、新規採番） | 旧 ID → 新 ID の対応表を残す（公開 URL に ID を使っているなら必要） |
| `created` / `updated` / 公開日時フィールド | `createdAt` / `updatedAt` / `publishedAt` | 作成 API の `publishedAt` 指定は Editor 以上で可 |
| HTML 本文 | Portable Text | HTML → Portable Text 変換が要る（EmDash の WordPress 取り込みは Gutenberg 用の変換器を持つが、汎用 HTML 用は未確認） |
| ファイルフィールド | メディア（アップロード API）+ 画像フィールドの `{ id, alt }` | ファイルを API でアップロードし、返った ID を参照に入れる |
| ユーザー | Discord 経由の初回ログインで自動作成 | 事前移行は不要（著者の対応付けは email） |
