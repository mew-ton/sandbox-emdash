# EmDash 採用可否 — 総括

調査対象: emdash 1.3.1（2026-10-18 公開）、Astro 7.4.2、Node 24.22.1。すべてローカル（Node / ローカル Docker）で検証した。
Discord は実物を使わずモックで検証した（実物で手元確認する手順は [`providers/discord/README.md`](../providers/discord/README.md)）。

## 推奨

**構成案 A（headless + `cms-client` 維持）を推奨する。ただし下の意思決定 D1・D2 を前提とする。**

要件の判定表どおりに読むと、項目 1 の 1-7（ユーザーがエクスポートで戻らない）が不合格のため、A の成立条件「項目 1〜4 がすべて合格」は満たしていない。
1-7 は EmDash の仕様（サイトエクスポートは認証データを持ち出さない）によるもので、構成案 B（統合）にしても変わらない。
見送りの条件（2-2 / 2-3 / 2-5 / 2-6 の不合格）には該当しない。

## 項目ごとの結果

| 項目 | 結果 | 要点 | 詳細 |
|---|---|---|---|
| 1. headless 運用 | 1-7 不合格、1-8 一部不合格、他は合格 | 読み取り・フック・スキーマ管理は成立。読み取りトークンは Subscriber のサービスアカウントで作る必要がある。エクスポートはユーザーを含まない。運用で使う 3 ルートが OpenAPI 未掲載 | [01-headless.md](01-headless.md) |
| 2. Discord 認証 | 全項目合格 | プロバイダ + ガード middleware で不変条件 1〜6 を満たした。他経路の封鎖は EmDash の注入ルートのパスに依存 | [02-discord-auth.md](02-discord-auth.md) |
| 3. cms-client | 3b 合格 | 契約を変えずに内部だけ REST 版へ差し替えられた。3a は公開サイトが EmDash アプリ化し、ID・画像・件数の扱いも変わる | [03-cms-client.md](03-cms-client.md) |
| 4. メモリ | 4-1〜4-5 合格、4-6 未完 | 350 MiB 制限でスワップの有無にかかわらず OOM なし。待機時の定常 RSS 約 125〜129 MiB、全シナリオのピーク 289 MiB。24 時間放置は 46 分で打ち切り、合否未判定（その間の変動は 1 MiB 程度）。workerd サンドボックスを有効にすると待機時に約 126 MiB 増える | [04-memory.md](04-memory.md) |

| 構成案 | 成立条件 | 状況 |

## 意思決定が要る事項

| # | 事項 | 選択肢 |
|---|---|---|
| D1 | 1-7: 全データの退避・復元をどう定義するか | (a) ユーザーを含む完全復元は SQLite のオンラインバックアップ + `uploads/` で行い（1-7e で全件復元を確認）、`site export` はコンテンツ移送用と位置づける / (b) 要件どおり「エクスポートでユーザーまで戻る」を必須とし、A も B も不成立とする |
| D2 | 1-8: OpenAPI 未掲載のルート（API トークン発行、招待、メディアファイル配信）への依存を許容するか | (a) トークン発行・招待は admin 画面で手作業とし、自動化しない（cms-client が依存するのは掲載済みの読み取り経路と、文書化された `url` 値のみ）/ (b) 不可とする |
| D3 | 一般メンバーを Editor にすることで生じる権限（タクソノミー・メニュー等の作成更新、他人の記事の公開・非公開化）を許容するか | 許容 / 公開操作もガードで制限する（追加実装） |
| D4 | Discord API に到達できないとき、ログイン中のセッションを上限時刻まで維持するか | 維持（現状）/ 拒否 |
| D5 | cold-standby 用のメール送信手段 | 非公式プラグイン（各 1 名メンテナ）/ 自作 |
| D6 | EmDash 更新時に注入ルートの差分を確認する運用 | 受け入れる / 受け入れない（ガードの網羅性を保証できなくなる） |
| D7 | メディアファイル配信が認証なしで、下書きでしか使っていない画像も URL を知っていれば取得できること | 許容 / 別ストレージ・プロキシで制限 |
| D8 | 4-6（24 時間放置）が未完であること | 計測スクリプトはそのまま再実行できる。採用判断の前に 24 時間分を取り直すか、46 分の観測で足りるとするか |
| D9 | サンドボックス用プラグイン（workerd）を将来使う可能性 | 使うなら待機時で 250 MiB を超えるため、1 GB プランが前提になる |

## 構成案 A で必要になる作業

### スキーマの移行

- `articles` / `casts` を EmDash の seed（`cms/seed/seed.json`）として定義する（このサンドボックスの定義は検証用の最小形）
- PocketBase のフィールドとの対応: リッチテキスト → Portable Text、ファイル → メディアライブラリ + 画像フィールド、select → select、カンマ区切り → string、JSON → json
- スキーマ変更の手順: admin か CLI で変更 → VPS 上で `emdash export-seed` → 差分をコミット

### cms-client

- 本番の PocketBase 版 `cms-client` の `.d.ts` と、このサンドボックスの `cms-client/dist/index.d.ts` を突き合わせる（`ColorThemeBase` / `FetchOptions` / `Cast` は仮定義）
- private registry への公開設定、`CMS_URL` / `CMS_TOKEN` を CI の secret に登録
- 読み取りトークンの発行手順（サービスアカウントを Admin で招待 → トークン発行 → Subscriber へ降格）を運用手順に入れる

### 認証・cold-standby の再設計

- 本番用 Discord アプリ（client secret、redirect URI）、Bot（再確認を使う場合）、ロール ID の登録
- 実 Discord で未確認の 2 点（PKCE の受け付け、Bot での単一メンバー取得に特権 Intent が要らないこと）を確認
- メール送信プラグインの選定（D5）と、cold-standby の切替手順（env を `on` にして再起動、戻すときも再起動）
- セットアップは `EMDASH_SETUP_TOKEN` を設定してから行う。可能なら公開前に VPS 内で済ませる

### 運用手順の改訂

- バックアップ: SQLite のオンラインバックアップ（`sqlite3 .backup` / `node:sqlite` の `backup()`）と `uploads/` を定期取得（D1 で (a) の場合）
- 公開・非公開化・削除で CI を起動するフックの dispatch 先と token を env に設定。dispatch 失敗時の再試行が無いので、定期ビルドを併用する
- 運営の追加は `EMDASH_ALLOW_INVITES=on` で再起動 → 招待 → 受諾 → `off` で再起動
- EmDash の更新時: 注入ルートの差分確認（D6）、`emdash types` / OpenAPI からの型再生成、項目 1〜3 の検証スクリプトの再実行

### データ移行（範囲外のため変換規約の下書きのみ）

| PocketBase | EmDash | 変換 |
|---|---|---|
| レコード ID | エントリ ID（ULID、新規採番） | 旧 ID → 新 ID の対応表を残す（公開 URL に ID を使っているなら必要） |
| `created` / `updated` / 公開日時フィールド | `createdAt` / `updatedAt` / `publishedAt` | 作成 API の `publishedAt` 指定は Editor 以上で可 |
| HTML 本文 | Portable Text | HTML → Portable Text 変換が要る（EmDash の WordPress 取り込みは Gutenberg 用の変換器を持つが、汎用 HTML 用は未確認） |
| ファイルフィールド | メディア（アップロード API）+ 画像フィールドの `{ id, alt }` | ファイルを API でアップロードし、返った ID を参照に入れる |
| ユーザー | Discord 経由の初回ログインで自動作成 | 事前移行は不要（著者の対応付けは email） |
