# 項目 4. メモリ制限下での稼働

対象: `cms/` の本番ビルド（`dist/` と本番依存のみのイメージ。`bench/prepare.sh` + `bench/Dockerfile`）。
計測: ローカル Docker（cgroup v1）、`mem_limit: 350m`。スワップなし（`memswap_limit: 350m`）と、ホストに 1 GB のスワップファイルを有効にしたうえでのスワップ 512 MB（`memswap_limit: 862m`）。
サンプリングは 1 秒間隔で、node プロセスの `VmRSS` / `VmHWM`（`/proc/<pid>/status`）と cgroup の値（`docker stats` と同じ「使用量 − inactive_file」）を記録した。
生データは `bench/results/<run>/samples.csv`、集計は同じ場所の `summary.json`。

## 結論

4-1〜4-5 はスワップの有無にかかわらず合格した。OOM・再起動は 0 回。待機時の定常 RSS は約 126〜129 MiB、全シナリオを通したピーク RSS は 289 MiB。
スワップ有りの計測でもスワップは一度も使われなかった（ピーク時でも上限に届かないため）。
4-6 は 2026-11-03 に 6 時間を完走した。立ち上がり後 0.13 MiB/時 の一定の増加が続き、**合格基準「単調増加しない」は満たさない**。率は小さく、定期再起動で無害になる（下記）。
4-7（workerd サンドボックス）を有効にすると、待機時でコンテナ全体の RSS が約 126 MiB 増える。

Node のヒープ上限（`--max-old-space-size`）の調整は不要だった。

### 4-6 長時間の放置

2 回測っている。1 回目（2026-10-25、コンテナ、`bench/results/bench-24h`）は 46 分で打ち切り、傾き +0.51 MiB/時 で合否は出していない。
2 回目（2026-11-03、`bench/results/host-6h`）は 6 時間を完走した。**要件が書いた 24 時間ではなく 6 時間で切り上げている**（理由は下記）。

計測方法が違う。`bench/run.mjs` はこのマシンで動かない（`docker compose` と cgroup v1 を前提とし、ここは podman と cgroup v2）。
代わりに `bench/host-sample.mjs` が `systemd-run --user --scope -p MemoryMax=350M` で同じ制限の cgroup v2 スコープに本番エントリを置き、`VmRSS` を 1 秒間隔で記録する。

**制限をかけることが本質的だった。** Node は使えるメモリからヒープ上限を決めるため、制限の有無で待機時の曲線が変わる。

| | V8 ヒープ上限 | 27 分の傾き |
|---|---|---|
| 制限なし（このホストは 30 GB） | 4288 MiB | +11.2 MiB/時（単調増加） |
| `MemoryMax=350M` | 259 MiB | — |

制限なしの数値は 16 時間で VPS を使い切る漏れに見えるが、V8 が 4.3 GB の天井に対して GC を遅らせているだけである。制限下で測り直した。

**結果**（6 時間、21502 サンプル、OOM 0 回）

| | 値 |
|---|---|
| VmRSS 開始 / 終了 | 154.3 / 154.6 MiB |
| VmRSS 最小 / 最大 | 150.8 / 154.6 MiB |
| VmHWM | 155.4 MiB（最初の 30 分で到達し、以後 5.5 時間動かない） |
| cgroup `memory.current` | 56.6 → 58.1 MiB |
| OOM | 0 |

窓ごとの傾きが結論を決めた。

| 区間 | 傾き |
|---|---|
| 0〜1h | +2.238 MiB/時 |
| 1〜2h | +0.112 MiB/時 |
| 2〜4h | +0.131 MiB/時 |
| 4〜6h | +0.128 MiB/時 |
| 1〜6h | +0.139 MiB/時 |

**立ち上がり後は平坦にならず、0.13 MiB/時 の一定の増加が続く。** 減速していないので収束曲線ではない。
RSS が前サンプルより下がったのは 21502 回中 2 回だけで、実質的に単調増加である。
1 回目の +0.51 MiB/時 は立ち上がり区間（0〜1h が +2.24 MiB/時）の平均で、待機時の真の率ではなかった。

**判定: 合格基準「RSS が単調増加しない」を満たさない。** ただし率は 0.13 MiB/時 で、350 MiB までの余裕 195 MiB を使い切るのに約 62 日かかる。

| 再起動間隔 | 間隔中の増加 |
|---|---|
| 毎日 | +3 MiB |
| 週 1 回 | +22 MiB |
| 月 1 回 | +94 MiB |

**定期再起動で実務上は無害になる。** EmDash 1.3.1 のビルド成果物に `setInterval` が 1 つもなく、予約投稿もクエリ時に評価されるため（F-27）、再起動が発火ウィンドウを跨いで予約投稿を落とす危険がない。起動は 1 秒で、公開サイトは静的配信なので閲覧者に影響しない。

増加の原因は特定していない。要求は健康確認の 1 回だけで、`setInterval` も無く、ミドルウェアも動いていない。V8 のヒープ断片化か SQLite のページキャッシュが候補だが、裏付けていない。

**6 時間で切り上げた根拠**: 判別したいのは「余裕 195 MiB を 1 ヶ月で使い切る率」= 0.31 MiB/時 である。6 時間なら 0.31 MiB/時 は 1.9 MiB の上昇として現れ、観測されたノイズ（分単位で 0.12 MiB）の 15 倍なので判別できる。年単位の creep（0.025 MiB/時）は分解能を下回るが、その速さなら通常のアップデート再起動で解消する。

**この計測が答えていないこと**: 待機時だけを見ている。4-2（編集 30 分）では 185 → 212 MiB と 30 分で 27 MiB 増えており、**負荷時の蓄積は待機時より 2 桁速い**。そちらはピークが 350 MiB を超えないことだけを確認しており、長時間の編集での推移は測っていない。

計測対象のビルドは `2f53532`（capability 修正後）で、その後の `ef557da`（アップロードのメッセージ）より前である。どちらも待機時のメモリには関係しない。

### 4-7 サンドボックス用プラグインの比較（合否に使わない）

`@emdash-cms/sandbox-workerd` 0.9.5（メンテナ 2 名）と workerd 1.20261009.1 を加え、最小の sandboxed プラグイン（`content:afterSave` フック 1 つ）を
有効にしたビルド（`VARIANT=sandbox bench/prepare.sh`。`cms/` 自体には入れていない）と、標準ビルドを同じ手順（セットアップ → 待機 2 分 → 記事 20 件作成 → 1 分）で比べた。

| | 標準 | サンドボックス有効 | 増加 |
|---|---|---|---|
| 待機時 node VmRSS | 129.7 MiB | 164.8 MiB | +35.1 MiB |
| 待機時 コンテナ内全プロセスの RSS 合計（node + workerd） | 129.7 MiB | 255.4 MiB | **+125.7 MiB** |
| フック実行後 全プロセス RSS | 131.9 MiB | 270.9 MiB | +139.0 MiB |
| 本番依存 node_modules | 595 MB | 919 MB | +324 MB |

サンドボックスを有効にすると、待機時点で全プロセス合計が 4-1 の基準（250 MiB）を超える。

## 観察した事実

- `docker stats` の値は node の VmRSS より 50〜60 MiB 小さい（VmRSS は node 本体や共有ライブラリのファイル由来ページを含み、cgroup ではそれがキャッシュ側に計上されるため）。合否は VmRSS で判定した
- 4-2 の 30 分間で VmRSS は 10 分ごとの平均で 189.8 → 200.1 → 207.2 MiB と増え、増え方は小さくなっていった。負荷後に放置したときに戻るかは測っていない
- 本番依存の `node_modules` は 595 MB（`emdash` が Astro・React・tiptap などを実行時依存に持つため）。512 MB プランのディスク容量の見積もりに入れる必要がある
- 計測は 4 コアの開発コンテナ上のローカル Docker で行い、2 系統を並行して実行した。CPU 性能やディスクが VPS と異なるため、所要時間は参考値
