# 残っている検証作業

調査を完了させるために残っている作業。採用後に必要になる構築作業は [`00-summary.md`](00-summary.md) の「構成案 A で必要になる作業」にある（別物）。

**前提**: このリポジトリは採用可否のサンドボックスで、求められているのは各要件を個別に検証した事実と証拠であり、最新のコードが全項目を通ることではない。既に得た証拠は、コードが先へ進んでも失効しない（[`00-summary.md`](00-summary.md#検証の証拠)）。

したがってここに挙げるのは「グリーンに戻す作業」ではなく、**まだ証拠が無い要件**と、**証拠を取りに行くときに邪魔になるもの**である。

各項目は「目的 / 手順 / 前提とブロッカー / これで埋まるもの」で書く。

---

## O-1. 計測器を現在の仕様に追従させる（必要になったときに）

**目的**: `verify/item1` と `verify/item5` は現在の仕様に追従していないため、**いま回すと落ちる**。既存の証拠は有効なので急ぎではないが、新しい証拠を取りに行くときに邪魔になる。

| スクリプト | 追従していない箇所 |
|---|---|
| `item5` | `5-1a` が「塞いだルートは匿名に 404」を検査する。無効機能は全員に 403 `FEATURE_DISABLED` に変えた。要件 5-1 の基準は「404/403」なので**設計は基準内**で、検査だけが古い |
| `item1` | 1-7 のインポートがリレーションにより拒否され、例外で停止する（O-2） |
| `item2` | 追従不要。ただし Discord 先行の順序（F-07）を通らないため、その経路の検査が無い |

**手順**: `item5` の `5-1a` を「匿名に 404 の系統」と「全員に 403 の系統」の 2 つに分ける。`item2` には Discord 先行でのログインが `SETUP_INCOMPLETE` になる枝を足す。

**前提とブロッカー**: なし。ただし**これ自体は新しい証拠を生まない**。やるのは、証拠を取りたい # が出てきたときか、計測器を資産として残したいときでよい。

**計測器を回すときの共通の前提**

```sh
cd cms && pnpm build && cd ..        # dist が必要
cd cms && node ./node_modules/astro/bin/astro.mjs dev stop   # 4321 の衝突を避ける
node verify/item2-discord.mjs --out reports/generated/02-discord-auth.md
```

- `verify/` の依存が必要。playwright を宣言に追加し、chromium 1248 を取得済み（2026-11-03）
- スクリプトは自分でモック Discord と CMS を起動し、空の一時 DB を使う。`cms/data.db` や `cms/.env` には触らない

## O-2. `verify/item1` をリレーションがある構成で完走させる

**目的**: 1-7 で異常終了して 1-8 以降が実行されない状態を解消する。

**背景**: `seed/seed.json` に `relations` を足したため、`emdash site import` が `TRANSFER_TARGET_NOT_EMPTY` で拒否される（[`01-headless.md`](01-headless.md) の「リレーションがインポートを阻む」）。スクリプトは `pnpm site import` の失敗を例外として投げて終了する。

**手順**

1. `verify/item1-headless.mjs` の 1-7 のインポート段を、拒否を**期待される結果として記録**して続行する形に直す（`1-7b` / `1-7c` のコンテンツ・メディア比較は実行できなくなるので、「リレーションを含む構成では検証不能」と記録する）
2. インポート経路そのものを確認したい場合は、リレーションを除いた seed で別インスタンスを立てる枝を足す

**前提とブロッカー**

- どちらの記録の仕方を正とするかの判断が要る。1-7 は既に不合格なので、合否は変わらない。影響するのは「何を根拠に不合格と言うか」

**これで埋まるもの**: 1-1・1-8 の鮮度（1-2〜1-6 は 1-7 より前に実行されるので、O-1 と同じビルドで既に通っている可能性が高いが、未完走のため記録されていない）。

## O-3. 本日追加したプラグイン 3 つの実機確認

**目的**: ロジックは単体で検証済みだが、admin から実際に使ったときの挙動を確認していない。

**手順**: dev サーバーを起動し、ブラウザで操作する。

```sh
cd cms && node ./node_modules/astro/bin/astro.mjs dev stop; pnpm dev
```

| 対象 | 操作 | 期待 |
|---|---|---|
| `portable-text-policy` | `articles` の本文にコードブロックを入れて保存 | `"Body" contains a code block.` |
| | テーブル / HTMLを挿入 / 引用 / インラインコード | それぞれ対応するメッセージ |
| | 見出し → h1 | `"Body" contains a level-1 heading.` |
| | h2〜h4・太字・斜体・リンク・箇条書き・画像 | 保存できる |
| `image-dimensions` | `casts` の `avatar` に 3840×2160 以外の画像 | `"Avatar" must be exactly 3840x2160px. "<名前>" is <W>x<H>px.` |
| | `avatar` を触らず `name` だけ編集 | 保存できる（未変更フィールドを再検査しない） |
| `webp-only` | Tools → Convert images に PNG を投入 | WebP としてライブラリに入り、表に変換前後のサイズが出る |
| | メディアページから PNG を直接アップロード | 拒否され、変換ページへ誘導するメッセージが出る |
| | 4K の実物で変換 | 完了する。所要時間とファイルサイズを記録（F-24 の実測値を置き換える） |

**前提とブロッカー**

- `.env` に `EMDASH_SITE_URL` が必要（設定済み）
- `su` でログインする。Discord の Editor アカウントでも同じ結果になるはずだが、**Editor 目線での確認は別途価値がある**（無効化した 8 機能の API が 403 になり、サイドバーから消えていること）
- 下線・取り消し線は現在拒否される（O-5 の判断待ち）。テスト中に意図しない拒否に見える

**これで埋まるもの**: 本日の実装が実際に効くことの確認。要件番号としては 5-1（権限範囲）と 1-6（`options` がプラグインから読めること）に跨る。

## O-4. 実 Discord での 2-4 と 2-6

**目的**: モックでのみ合格している 2 項目を実物で確認する。2-6 は README が挙げる最後の未確認事項（Bot の特権 Intent）も解消する。

**手順**

**2-4（権限モデル）**

1. テスト用 Discord サーバーに、一般ロールのアカウントとリーダーロールのアカウントを用意する
2. 一般ロールでログインし、他メンバーの記事を編集（200 を期待）、削除（403 を期待）
3. リーダーロールでログインし、削除（200 を期待）
4. UI ではなく API 直叩きでも同じ結果になることを確認（要件が「サーバー側でも同じ結果」を求めている）

**2-6（セッション無効化）**

1. `.env` に `DISCORD_BOT_TOKEN` を設定し、Bot をテスト用サーバーへ招待する
2. `DISCORD_REVALIDATE_SECONDS` を短く（例 30）して再起動する
3. ログイン中に Discord 側でロールを外す、またはサーバーから抜ける
4. 次の再確認で拒否されることを確認する
5. **Bot で `GET /guilds/{guild}/members/{user}` を呼ぶときに特権 Intent が要るか**を確認する（README の未確認事項）

**前提とブロッカー**

- テストアカウントが 2 つ以上必要（ロール違い）。ロールを持たないアカウントもあると 2-2 の確認を兼ねられる
- Bot の作成と招待が必要（2-6 のみ）
- 2-6 は待ち時間が発生する

**これで埋まるもの**: 2-4・2-6 を実物で裏付ける。`providers/discord/README.md` の未確認事項が全て解消する。

## O-5. 下線・取り消し線・文字揃えの扱い

**目的**: `articles.body` の `allowedMarks` が現在 `strong` / `em` / `link` のみで、**下線と取り消し線が拒否される**。これが意図かを決める。

文字揃え（`textAlign`）は現在検査していない。制限するなら `portable-text-policy` に 5 番目の軸を足す。

**前提とブロッカー**: 判断のみ。実装は 1 行。

**これで埋まるもの**: O-3 のテストが意図した結果になる（いまは下線で拒否されるため、テスト中に誤検知に見える）。

## O-8. ツールバーからの不要項目の非表示

**目的**: `portable-text-policy` は保存時に拒否するが、ツールバーからは消えない。編集者は使えてしまい、保存時に止まる。

**手順**: 見出しドロップダウンを開いた状態の DOM が必要（h1 / h5 / h6 を個別に隠すため）。それ以外のボタンは `aria-label` を足場にできるが、日本語と英語が混在しており**ロケールに結合する**。

**前提とブロッカー**

- DOM の提供が必要
- TipTap のキーボードショートカットと Markdown 入力規則（` ``` `、`# `）は CSS では塞げない。**拒否が本体で、非表示は補助**という関係は変わらない
- CSS はページ全体に注入されるため、フィールドごとに違う方針は適用できない（現在 `portableText` は `articles.body` の 1 つだけなので問題にならない）

**これで埋まるもの**: 編集者の体験。要件番号には紐づかない。

## 優先順位

**採用判定に本当に必要なのは O-6（4-6）だけ**である。要件 §3 の成立条件は項目 1〜5 の合格で定義されており、4-6 が未完のままでは構成案 A も B も成立しない。他の # は証拠が揃っている。

| 区分 | 項目 | 理由 |
|---|---|---|
| **判定に必要** | O-6 | 4-6 が唯一「証拠が存在しない」合格基準 |
| 証拠が無く、判定に影響する可能性 | O-7 | 5-2 は検証済みだが、F-08（生 HTML / iframe）を踏まえた再評価をしていない |
| 本日の実装が効くかの確認 | O-3、O-5 | 合否は変えない。効いていなければ、5-1 と 0-3 の「対策込み」という記述の裏付けが弱くなる |
| 証拠の上積み | O-4 | モックで合格済みの # を実物で裏付ける。README の未確認事項（Bot の特権 Intent）が解消する |
| 資産の整備 | O-1、O-2 | 新しい証拠は生まない。計測器を再利用可能に保つための作業 |
| 可読性 | O-8、O-9 | 検証とは無関係 |

O-1 と O-2 を「やらなければならない作業」として扱わないこと。計測器が落ちている状態は、既に得た証拠を損なわない。
